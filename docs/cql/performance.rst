===========
Performance
===========

CQL generates, at compile time, a per-model *scanner* that copies each row from
the database into your Go structs **without reflection**. gorm — and tools built
on top of it such as `gorm-gen <https://gorm.io/gen/>`_ — instead scan every row
reflectively at run time. The larger the result set, the more that difference
adds up.

Benchmarks
==========

gorm ships its benchmarks as plain ``go test -bench`` functions
(``gorm/tests/benchmark_test.go``) and reports the raw Go output — ``ns/op``,
``B/op`` and ``allocs/op``. CQL's suite (``cql/benchmarks``) mirrors gorm's seven
benchmarks over the same ``users`` table, so the two can be compared line for
line. Each library is measured with its **own** suite:

* **CQL** — ``cql/benchmarks`` (this repo).
* **gorm** — gorm's own ``tests/benchmark_test.go``, run against **upstream gorm
  v1.31.2** (not CQL's fork).
* **gorm-gen** — a DAO generated by `gorm-gen <https://github.com/go-gorm/gen>`_
  over the same table, also on gorm v1.31.2. gorm-gen only ships the two read
  shapes below, so it appears only in those rows.

All were produced on the same machine (Apple M4 Max), against an on-disk SQLite
database. Absolute nanoseconds vary by machine — what matters is CQL versus the
alternatives on the *same* hardware.

Reading the results
===================

* **Multi-row reads (``ScanSlice`` / ``ScanSlicePointer``) — the big win.**
  Materialising 10,000 rows, CQL is about **27% faster** and does about **37%
  fewer allocations** than gorm. This is the generated scanner paying off: it
  never falls back to reflection while filling the structs. This is the common
  case for list queries, and the reason the fast scanner exists.

* **Writes (``Update``, ``Delete``) — a modest edge.** CQL is ~13% faster on
  ``Update`` and ~8% faster on ``Delete``, with roughly half the allocations on
  ``Delete``. ``Create`` is a wash (within noise) — write cost is dominated by
  disk I/O, so the scanner has little to contribute.

* **Single-row reads (``Find``, ``Scan``) — a tie.** For one row the per-query
  cost dominates and all three land within a handful of nanoseconds of each
  other. gorm's ``Scan`` is marginally ahead because it runs raw SQL straight
  into one struct (CQL has no raw-SQL surface, so it goes through the same typed
  ``Query`` path as ``Find``). The scanner's advantage only shows up once a query
  returns many rows.

Extended scenarios
==================

``cql/benchmarks/extended_bench_test.go`` covers cases that don't map onto
gorm's canonical seven — multi-condition ``WHERE``, ``First()``, and the two
association-loading paths where the generated scanner is expected to help most:
a **has-one joined preload** (single ``JOIN`` query) and a **has-many preload**
(one child ``SELECT`` after the parent scan). gorm doesn't ship benchmarks for
these, so the gorm column below comes from equivalents that live in the fork at
`tests/extended_bench_test.go
<https://github.com/FrancoLiberali/gorm/blob/2e3b5fb/tests/extended_bench_test.go>`_
(``.Joins("Account")`` for the has-one, ``.Preload("Pets")`` for the has-many,
against gorm's own ``User``/``Account``/``Pet`` models). The numbers were
measured on gorm v1.31.2; the fork's optimizations are additive helpers that
these plain ``Where``/``Joins``/``Preload``/``Find`` paths never touch, so the
baseline is unchanged from upstream.

The pattern is the same as the core suite, and sharper on associations:

* **Association loading is CQL's strongest case on allocations.** Both preload
  paths allocate **~35–50% less** than gorm (has-many ``50×4``: 2,736 vs 5,505;
  joined preload ``1K``: 21,513 vs 34,215). On wall-clock, CQL is ~11% faster on
  the has-one join at 100 rows and ~23% faster on the has-many at ``50×4``.

* **Multi-row WHERE dispatch** is ~22% faster at 100 rows with ~36% fewer
  allocations.

* **Ties are still ties.** Single-row shapes (``WHERE`` ×5 on 1 row, ``First``)
  and the 1K-row joined preload come out even on wall-clock — dominated by query
  and JOIN cost — though CQL still allocates less in every one.

* **One case where gorm is leaner:** ``WHERE`` ×5 on a *single* row allocates
  slightly fewer for gorm (149 vs 166). CQL's per-condition dispatch carries a
  small fixed setup cost that only pays for itself once the query returns many
  rows.

Why gorm-gen tracks gorm
========================

gorm-gen adds a type-safe query-building API, but the generated code executes
queries through gorm's runtime and therefore uses gorm's reflective scanner. Its
per-row scan cost is, by construction, the same as gorm's — the ``ScanSlice``
allocation counts above (190,097 for gorm vs 189,781 for gorm-gen) are within
noise of each other. CQL replaces exactly that reflective step with generated
code, which is what produces the difference.
